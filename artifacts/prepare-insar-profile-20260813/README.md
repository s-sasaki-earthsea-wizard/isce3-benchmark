# prepare-insar-profile-20260813 — where prepare_insar_hdf5's 562 s goes

Evidence for issue
[#32](https://github.com/s-sasaki-earthsea-wizard/isce3-benchmark/issues/32)
Steps 1+2: the GUNW-chain `prepare_insar_hdf5` occurrence #1
(557.4 s CPU / 562.5 s GPU = 14 % of the GPU wall in the run2 pair, see
[`reports/2026-08-insar-gpu-cpu-equivalence.md`](../../reports/2026-08-insar-gpu-cpu-equivalence.md))
is dominated by `generate_insar_mask()`
(`python/packages/nisar/products/insar/utils.py:497`, isce3 v0.25.16),
a pure-Python per-pixel double loop — **89.0 % of profile samples**.
The issue's original hypothesis (compression filter / fill-value writes
at dataset allocation) is refuted.

## Headline numbers

- Standalone rerun wall: **446.540 s** (journal; in-workflow occurrence
  #1 was 562.5 s — do not use 446.5 as an improvement denominator, the
  Δ≈116 s is not yet decomposed).
- 40,626 samples @ 100 Hz ≈ 406 s CPU-active → **~91 % CPU-bound**.
- Attribution (full tables in `pyspy_attribution_tables.txt`):

| share | ≈ s | where |
|---|---|---|
| 74.0 % | 301 | RIFG interferogram mask, 6840×10581 = 72.4 Mpx |
| 11.3 % | 46 | RUNW interferogram mask, 2565×4069 = 10.4 Mpx |
| 3.7 % | 15 | pixelOffsets masks (545×703, RIFG + RUNW) |
| 2.8 % | 11 | `generate_dem_rdr` (GPU topo, offsets + igram DEM) |
| 1.8 % | 7 | `save_to_hdf5_ds` |
| 4.4 % | 18 | geolocation cubes (L1) + radar grid cubes (L2, GUNW) |
| 1.3 % | 5 | `compute_stats` |

- Sample ratio RIFG/RUNW igram masks = 6.55 ≈ pixel ratio 6.94 →
  **cost is linear in pixel count**. This also explains the freq-B
  iono-chain prepare proper at 38 s, and the CPU/GPU 0.99x parity
  (the dominant term is Python, identical on both paths).
- Per-pixel unit cost: 72.4 Mpx / 301 s ≈ **4.2 µs/px** — one loop
  iteration = 2 pybind `SubSwaths.get_sample_sub_swath` calls
  (`utils.py:352,358`) + interpreter overhead + `list.append`.
- Total `generate_insar_mask` = 36,165 samples ≈ **361.7 s** standalone.
  Mask-only projection for in-workflow occurrence #1:
  562.5 − 361.7 ≈ 201 s (≈ 182 s if the per-call re-read of
  `inputDataExceptionMask` — ~19 s sampled — is also cached).

## Provenance

- Host: nucbox-evo-t1 (RTX 5080 16 GiB, 16 threads); isce3 v0.25.16
  from-source CUDA build (`ISCE3_SRC=.../isce3-v0.25.16`,
  `ISCE3_BUILD_DIR=./isce3-build-v0.25.16` passed as command-line env
  overrides — `.env` untouched); numpy 1.26.4 (pre-NEP-50: the
  intended, non-[isce3#335](https://github.com/isce-framework/isce3/issues/335)
  mask-bit behaviour is what ran).
- Pair: NISAR ASC 139/019 2026-07-05 → 2026-07-17 (Boso), freq A HH —
  same runconfig as run2
  (`nisar-displacement/configs/insar_gunw_ASC139_019_20260705_20260717_gpu.yaml`).
- Scratch seeding (occurrence-#1-like, i.e. NO nested rdr2geo/geo2rdr):
  `~/scratch/gunw_ASC139_019_gpu3/geo2rdr` (freqA range/azimuth.off,
  17.4 GB each) mounted read-only at `/scratch/geo2rdr`; fresh NVMe
  dirs for `/scratch` and `/out`; `/data` on the NAS as in run2.
- Gotcha reproduced on purpose-in-reverse: prepare **writes**
  `scratch/rdr2geo/freq*/{RIFG,RUNW}_offsets_dem.rdr`
  (`InSAR_L1_writer.py:466`, `generate_dem_rdr`, GPU topo) — mounting
  `rdr2geo` read-only kills the run in 11 s. Leave `rdr2geo` writable.
- py-spy: `--format raw --rate 100 --subprocesses --nonblocking`
  (NOT `--native`: blocking/native sampling injects EIO on the CIFS
  data mount — see `scripts/run_profile_pyspy.sh` provenance notes).
